# Rework, September 2026

The work Nathan asked for after phases 0 to 6 were built and looked at. Eight
units, in dependency order. Each one is a commit or a small run of commits, and
each is verified with `npm run check` before the next one starts.

Keep this file honest. A unit is only ticked when it is built, checked and
looked at in both themes.

---

## 1. Navigation shell: a record opens full screen

- [x] `src/app/breadcrumb.tsx`: a context the shell owns and a screen feeds.
- [x] `TitleBar` renders `Juno / Screen / Record`, every segment but the last
      clickable.
- [x] Clients: choosing a client replaces the list with the record, full width.
- [x] Documents: the same.

Mail keeps its three panes and the calendar keeps its side panel, because both
are a row of something still being browsed (rule 5c, decision 30). Client
email, phone and address stay side panels for the same reason.

## 2. Mail templates and document templates are two screens

- [x] `TemplatesScreen` split into `MailTemplatesScreen` and
      `DocumentTemplatesScreen`. One list each, no shared content pane.

## 3. Notes edit the way Obsidian does

- [x] A live-styled Markdown editor: the styling is applied while typing, the
      markup is hidden until the cursor enters it.
- [x] Used wherever notes are typed: clients, events, reminders, projects.

## 4. Mail template editor

- [x] Preview a template from the list without opening the editor.
- [x] A visual editor over the template HTML, with a code view for anyone who
      prefers it, and the preview updating as it is edited.
- [x] Declared inputs on a template: name, label, type, required. Stored on the
      template, asked for when the template is used.
- [x] Images: a URL or a file. A file becomes base64, which is the wrong answer
      in an email, so it asks first and says why.

## 5. Using a template is its own screen

- [x] "Use" on a mail template: fill the inputs, link a client or no one,
      create the draft.
- [x] "Use" on a document template: the same, ending in a PDF.

## 6. Document template editor: pages, not a textarea

- [x] A page model: pages, a margin, and blocks inside it. Flowing blocks and
      absolutely placed boxes, like a PDF.
- [x] Text, headings, images, spacers, page breaks, tables.
- [x] Renders to the HTML the existing `printToPDF` pipeline already takes, so
      nothing below it changes.

## 7. A document is a PDF

- [x] Import an existing PDF as a document.
- [x] Generate from a template, which writes the PDF at generation.
- [x] Open, review, sign, and the signed PDF is saved beside it.

## 8. First run

- [x] A setup window on a genuinely empty install: welcome, your business,
      appearance, the lock, mail, done. Animated, and it degrades to nothing
      moving when the machine asks for that.
- [x] A walkthrough of the app afterwards, replayable from Settings.
- [x] `onboarding` in `settings.json`, so a reset or a clean install shows it
      again and a normal launch never does.

## What is thin, and known

Written down rather than left to be discovered.

- **The visual mail editor uses `document.execCommand`.** It is deprecated and
  it is still the only thing that edits a selection inside a `contentEditable`
  without pulling in an editor framework. It works in Chromium, which is the
  only engine this app runs in. If it is ever removed, the code view is the
  fallback that still works.
- **The page editor is not Word, on purpose.** No text wrap around an image, no
  columns inside a flow, no style sheet. The block set is the set.
- **A box is dragged with a mouse or typed in millimetres.** There is no
  keyboard nudge yet. The inspector's number fields are the accessible path.
- **The walkthrough points at sidebar entries.** A stop whose target is missing
  falls back to a centred card, which is what happens if the sidebar is ever
  reshaped again.
- **Mail has still never met a real server.** Unchanged by this work, and still
  the most valuable thing left to do. See TODO.md.
